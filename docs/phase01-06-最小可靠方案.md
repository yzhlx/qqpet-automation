## 一、第一阶段结论（技术可行性）

### 1.1 A 路线（原生文本读取）：**已排除，实测不可用**

| 测试 | 命令 | 结果 |
|---|---|---|
| 默认 dump | `uiautomator dump` | 只含 `com.ynk.virtualdisplay`，51 节点 |
| 指定 display 4 | `uiautomator dump --display 4` | 仍是 `com.ynk.virtualdisplay`，55 节点 |
| **启动 QQ 后 dump** | `am start ...AdelieFragmentActivity` + dump | **38,738 B，与第一次完全相同，仍只有我们自己的 app** |
| logcat 价格信息 | `logcat | grep 金币/价格/兑换` | **空** |

**架构原因**：游戏运行在 QQ 的 **`AdelieFragmentActivity`（小程序容器）** 中，
画面由容器自绘，**不产生无障碍节点**。QQ 宿主窗口 `mHasSurface=false`。

且现有架构**刻意不使用 Accessibility**（`HeadlessDisplayCapture.kt:24` 注释明示
"No MediaProjection / Accessibility / network"）。

**结论：不存在可访问的结构化数据入口。A 路线彻底不可用。**

### 1.2 B 路线（有限固定商品与金额的视觉校验）：**可行，且成本远低于预期**
前提是**把数量固定为 1**（见下）。

### 1.3 C 路线（新增数字识别）：**可行但成本高**，需金色模板 + 多位置 ROI（见 `phase01-04`）

## 二、关键成本洞察：**固定数量 = 消除 OCR 需求**

### 2.1 兑换食物的价格结构是有限的
| 商品 | 单价 | 效果 |
|---|---|---|
| 饼干 | **5 金币** | 体力+10，心情+1 |
| 虾 | **20 金币** | （更高） |

**若数量固定为 1**：
- 选饼干 → 合计 **5 金币**（固定）
- 选虾 → 合计 **20 金币**（固定）

**合计金额只有 2 种可能，无需读取任何数字。**

### 2.2 这带来一个重要的简化
原计划（`phase01-04`）需要按位置新建 4 组金色数字模板。
若数量固定为 1，则**完全不需要数字识别**，只需：

| step | 需要确认的 | 方法 |
|---|---|---|
| 1 | 当前是「兑换食物」弹窗（非洗澡） | 标题模板匹配 |
| 2 | 选中的是饼干（非虾） | 商品行模板匹配 |
| 3 | 数量 = 1 | 步进器区域模板匹配（"1"的单字符模板，深灰字，**现有暗色门禁可用**） |
| 4 | 合计 = 5 | 可选：用已知值 5 做**断言**，而非读取 |

第 4 步尤其关键：**不是"读取金额"，而是"确认画面与预期一致"** ——
这属于 B 路线（视觉校验），**不违背"不硬编码金额"的精神**，
因为金额是从**商品单价 × 数量**推导，而两者都被视觉确认。

> **但仍需你确认**：这种"确认而非读取"是否满足你的约束。
> 严格说，5 这个数字仍来自**观察到的游戏 UI**（我在截图中确实看到"5"），
> 但它现在是**代码常量**而非运行时读取值。这是需要你裁决的点。

## 三、推荐的最小实现（第二阶段）

### 3.1 推荐：**B 路线 + 固定数量 1**

```
护理前读属性
  ├─ 达标 → 不护理
  └─ 未达标 → 进护理页
        ├─ 正常喂食页 → 走既有已验证路径（不改）
        └─ 出现兑换弹窗
              ├─ 模板确认：是「兑换食物」还是「兑换洗澡道具」
              ├─ 模板确认：数量 == 1（若否 → 安全停止）
              ├─ 预算校验：单价(5 或 20) ≤ 50，累计 ≤ 100，余额 ≥ 100
              ├─ 点击「支付」
              ├─ 核验：金币扣减 或 属性提升（二者至少一可验证）
              └─ 任一不确认 → 安全停止，不重试支付
```

### 3.2 需要新增的资产（极少）
| 资产 | 说明 |
|---|---|
| `exchange_food_title.png` | 「兑换食物」标题区（已有帧可裁） |
| `exchange_soap_title.png` | 「兑换洗澡道具」标题区（**需采集**） |
| `qty_one.png` | 步进器数字"1"（深灰字，**现有门禁可用**） |
| `biscuit_selected.png` | 饼干选中态 |
| `pay_button.png` | 支付按钮（可选） |

**约 5 个小模板**，对比 C 路线的"4 组数字模板 × 多位置"少一个量级。

### 3.3 明确区分（按你的要求）

| 类别 | 本方案中的内容 |
|---|---|
| **运行时已确认的金额** | 合计 = 单价 × 数量，两者均经模板确认 |
| **仅根据历史截图推断的金额** | 饼干 5 金币 / 虾 20 金币 —— **来自我观察的截图，未运行时验证** |
| **无法确认的余额** | 金币余额 **437 是某时刻的快照**，非运行时读取 |

⚠️ **余额问题**：B 路线**读不到金币余额**（金色字，无模板）。
预算"购买后余额 ≥ 100"因此**无法强制**。
**这是必须你裁决的安全缺口**（见 §5）。

## 五、需要你明确批准的事项

### 5.1 安全缺口：余额不可读
B 路线读不到金币余额 → **"购买后余额不得低于 100 金币"无法强制**。

**可选替代保障**（需你选择或提出其他）：
| 方案 | 说明 |
|---|---|
| a. 用**会话内累计上限 100 金币**作为唯一硬约束 | 弱化余额下限，但总量受控 |
| b. 每次购买前**先截一次金币区**，人工/离线核验 | 不自动化，但每次可控 |
| c. 允许使用**已知余额快照**（437）并加余量 | 有风险，快照会过期 |
| d. **放弃购买，改为报告 BLOCKED** | 最保守，但闭环无法完成 |

### 5.2 金额来源的定性
"饼干 5 金币"来自我**观察截图**，将成为代码常量。
按你"不得凭假设硬编码"的要求，这需要你确认：
- 是否接受"**视觉确认商品，金额取自已观察的游戏 UI**"？
- 还是要求必须**每次运行时读取**金额数字（→ 回到 C 路线）？

### 5.3 数量能否固定为 1
需实测步进器是否可设 1。若可以，成本大幅下降。
