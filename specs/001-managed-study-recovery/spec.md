# Feature Specification: 打工、护理、学习独立运行与方案闭环

**Feature Directory**: `specs/001-managed-study-recovery`
**Created**: 2026-10-21
**Updated**: 2026-10-21
**Status**: Ready for planning
**Input**: 用户要求先修复本会话Android插件工具未暴露问题；后续验收打工、护理、学习三个动作各自独立运行，也能组合成方案闭环。本规格在原有托管开课与打工后学习范围上同步此要求。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 三个动作独立运行 (Priority: P1)

用户可以单独启动一次打工、一次护理或指定节数的学习；每次只执行所选动作并展示结果，避免为运行一个动作而被迫配置或执行其他动作。

**Independent Test**: 分别从用户入口启动打工、护理和学习；核对实际行为、完成证据和每日用时，确认没有隐式执行其他动作。

**Acceptance Scenarios**:

1. **Given** 已选岗位、岗位自身状态要求和每日剩余用时均满足，**When** 用户启动仅打工，**Then** 完成该岗位一班、确认正数工资到账并结束；不要求选择课程，不购买护理物品、不护理、不上课。
2. **Given** 用户设置护理阈值且必要物品或资金充足，**When** 启动仅护理，**Then** 护理至目标后结束；不要求课程或岗位，不打工、不上课；已达阈值的项目跳过。
3. **Given** 课程存在、可选，实际余额足以支付学费且每日剩余用时足够，**When** 启动仅学习，**Then** 仅完成所选课程和节数；不自动打工或护理；体力/清洁低于护理目标、读数未知或过期不构成学习阻塞条件。
4. **Given** 独立动作所需条件不足，**When** 检查到缺失条件，**Then** 以可理解的原因停止，提示所缺条件；不自动插入未选择动作。

### User Story 2 - 选择动作组成方案 (Priority: P1)

用户勾选需要的动作、配置各自参数并保存方案。执行时按显示顺序进行；用户能看到当前动作、逐项结果和整体完成或停止原因。

**Independent Test**: 保存并重新打开方案，逐项核对配置；启动各非空动作组合，确认执行顺序、跳过行为、结果与所选动作一致。

**Acceptance Scenarios**:

1. **Given** 已选择打工、护理、学习，**When** 启动方案，**Then** 按打工→护理→学习完成，确认工资到账、护理达标和课程完成；全部通过后才显示方案完成。
2. **Given** 只选择任意一个动作，**When** 保存并启动方案，**Then** 与相应独立入口遵循相同规则。
3. **Given** 选择打工+护理、打工+学习或护理+学习，**When** 启动，**Then** 只执行选中的两项并按显示顺序进行，不隐式插入第三项。
4. **Given** 方案前一项失败、结果不明确或被用户停止，**When** 流程结束，**Then** 不继续后续项，保留已完成项、失败项和未执行项各自的真实状态。
5. **Given** 方案已保存，**When** 用户重新打开应用，**Then** 所选动作、参数和顺序保持；重新打开方案本身不自动启动消费动作。

### User Story 3 - 按需打工兼容原有托管 (Priority: P1)

用户可继续使用现有“资金不足才先打工”的托管行为；也能明确选择先执行一班打工再继续方案，不因为当前金币充足而跳过显式安排的打工。

**Independent Test**: 分别验证资金不足时按需工作、资金足够时按需跳过、资金足够时显式工作，以及旧方案迁移后的显示与实际执行。

**Acceptance Scenarios**:

1. **Given** 含学习的方案设置为按需打工，且金币不足以覆盖学费和必要护理，**When** 启动，**Then** 完成一班已选岗位、确认工资、复核后续条件，随后完成选中的护理和学习。
2. **Given** 按需打工且资金已经足够，**When** 检查工作条件，**Then** 将工作记为因资金充足而跳过，继续已选择的后续动作。
3. **Given** 用户显式安排一班打工，**When** 当前资金已足够，**Then** 仍执行该班岗位；独立打工无需学习目标。
4. **Given** 工资未确认或一班后资金仍不足，**When** 即将继续后续消费，**Then** 停止并说明原因，不凭预期工资继续，不自行增加工作班次。
5. **Given** 旧托管方案被打开，**When** 迁移展示，**Then** 保持原课程、节数、护理目标、预算及原每轮护理/首轮按需工作安排；所有profile统一取消学习的强制体力/清洁及健康新鲜度门禁，护理配置只决定所选护理动作，不阻挡开课、学习恢复或已证实完成的登记。

### User Story 4 - 准确开课与结果确认 (Priority: P1)

用户选择课程后，期望实际进入该课程并完成学习，异常时得到明确结果。请求开课、确认开始和确认完成必须分别反映真实状态。

**Independent Test**: 在满足条件时完成田径运动课一节；另验证开课未确认与结果页已出现两类情况，确认不会误报完成或重复付费。

**Acceptance Scenarios**:

1. **Given** 所选课程存在、名称时长与当前详情一致且条件满足，**When** 执行学习，**Then** 真实完成课程后显示1/1，完成节数与用时记录不重复增加。
2. **Given** 请求开课后未能在现有确认期限内证实学习开始，**When** 超时，**Then** 以 `LEARNING_NOT_CONFIRMED_AFTER_START` 或更具体原因停止并保留现场，不自动重新付费。
3. **Given** 请求开始后首次可辨认的页面已经是结果页，**When** 核对本会话课程与结果证据，**Then** 仅在能证明归属与完成时接收为结果；不能归属则标记结果不明确并停止，不再次点击开课。
4. **Given** 档案与当前详情名称或时长不一致，**When** 即将开课，**Then** 停止并提示差异，不误开其他课程。

### User Story 5 - 恢复与安全停止 (Priority: P2)

用户希望方案在可识别入口跳出后有限恢复；遇到课程缺失、未知页面、资金或时间不足时，停止在正确位置并保留证据。

**Independent Test**: 验证正常返回、已识别入口重入、未知页面及恢复耗尽；对含学习方案使用不存在课程核对消费前停止，对不含学习方案确认课程缺失不构成阻塞。

**Acceptance Scenarios**:

1. **Given** 返回后出现已识别宠物入口，**When** 恢复，**Then** 确认进入房间后继续尚未完成步骤，不重复已确认消费。
2. **Given** 返回后仍是可识别地图遮挡，**When** 尝试恢复，**Then** 最多三次后回到房间或停止；未知页面不连续试点。
3. **Given** 含学习方案的课程不存在，**When** 启动前核对，**Then** 以 `COURSE_NOT_FOUND` 停止、完成0节，并且该方案未发生打工、护理购买或开课。
4. **Given** 仅打工或仅护理方案且课程档案为空，**When** 本动作自身条件满足，**Then** 正常运行，不因无关课程失败。

### Edge Cases

- 方案为空：不能启动，说明至少选择一个动作。
- 未选择动作的参数缺失：不得阻断方案；选中动作缺必要参数则在任何消费前拒绝启动。
- 打工前必须按同一次确认的岗位实际体力消耗、清洁消耗和固定时长，分别核对当前两项资源及剩余分钟；等于实际消耗可执行，任一不足或必要值未知/过期不可启动。岗位页面与已验证目录变化时停止，不按旧耗值放行。
- 仅学习不要求达到任何护理体力/清洁目标，不要求健康读数可用或新鲜；只在课程、学费、时间预算、页面身份或执行结果等必要条件不足时停止，不隐式打工/护理。课后健康观察失败不撤销已证实的课程完成。
- 工作/护理依赖的健康信息在长导航或工作后必须重新核对；学习健康仅作可选观察，不得由共用恢复逻辑重新引入健康门禁。
- 护理优先消耗已确认库存，仅为缺口购买；零金币但库存足够时可以护理，库存未知不能当零并直接购买，也不能把费用上界当成已证实缺钱。
- 确需购买时，在付款前确认真实钱包、商品数量及实际总价，并检查购买后足以保留后续全部未付学费；本会话购买额度不等于钱包余额。必要钱包不可确认则不付款，付款结果不明不得重付。
- 组合前推演工作耗体力/清洁、护理库存与购买缺口、剩余节数学费和分钟；每步结束按真实观察重建后缀需求。预测工资仅用于可行性分析，实际确认到账前不可花费；一班工资不足完成后缀则停止，不自行增班。
- 体力或清洁已达阈值：跳过该护理项目，记录无须护理，不进行无收益消耗。
- 工资页只有本次工资：可用明确正数工资确认到账；后续需要可用余额时独立重新确认，不能把本次工资当累计余额。
- 工作与学习超过每日剩余用时：拒绝开始超限活动；已启动或启动结果不明确的用时按现有保守规则保留，不因未确认成功自动退还额度。
- 断连、画面不可读、重启或停止：已完成项保留，未知执行结果不算完成，不自动重放未确认支付；停止不能撤销游戏中已开始的工作或学习。
- 同时启动独立动作和方案：只允许一个执行中的会话，后续启动被拒绝并显示当前执行项。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统必须提供打工、护理、学习独立启动入口，及选择动作运行方案的入口；每个独立入口只执行所选动作。（故事1、2）
- **FR-002**: 方案必须支持三个动作全部七种非空组合，顺序明确展示为打工→护理→学习并跳过未选项；空方案不可启动。（故事2）
- **FR-003**: 系统必须只校验所选动作的必要参数；独立打工和护理不依赖课程档案、课程名称或课程时长。（故事1、5）
- **FR-004**: 所有含学习方案必须在工作、护理购买或学习前预检所选课程存在且可选；不存在以 `COURSE_NOT_FOUND` 停止，不消耗资源。（故事5）
- **FR-005**: 显式打工必须完成已选岗位一班；按需打工仅用于含学习方案，资金充足时可带原因跳过，独立打工不能按课程资金条件跳过。（故事1、3）
- **FR-006**: 系统必须确认岗位完成和正数工资到账后才将工作记为完成；后续消费前必须确认实际可用资源，不能将工资金额当余额。（故事3）
- **FR-007**: 护理必须按用户阈值运行，已达阈值项目跳过；先使用已确认库存、仅购买缺口，未选择护理时不得隐式护理或购买护理物品。（故事1、2）
- **FR-008**: 所有profile的学习开课前必须核对课程名称、可选性、时长、实际学费余额与分钟预算，不强制体力/清洁值或健康新鲜度；未选择打工或护理时不插入动作，健康观测失败不能阻挡学习恢复或抹掉已证实完成。（故事1、4）
- **FR-009**: 系统必须区分请求开课、学习开始、学习完成；学习开始和完成均须有本会话证据，未确认不得重复点击付费或增加完成节数。（故事4）
- **FR-010**: 系统必须对请求开课后直接出现结果页的情况核对课程与会话归属；无法归属时停止并标记结果不明确。（故事4）
- **FR-011**: 工作与学习必须共用每日用时上限，开始前登记一次用时占用，结果不明时保守保留占用且明确展示；重复观察与恢复不得重复记账。（边界场景）
- **FR-012**: 系统必须在长导航或工作后刷新工作/护理实际依赖的健康信息，必要值未知或过期不得启动相应动作；学习健康观察可选，所有profile均不得复用该门禁阻挡学习。（故事2、3）
- **FR-013**: 系统必须确认返回页面身份；已识别入口允许重入，地图返回恢复最多三次，未知页面或超限停止，不能重放已确认消费。（故事5）
- **FR-014**: 系统必须保存方案选择、动作参数和执行顺序，兼容旧方案的护理+学习及可选按需工作语义，不因升级自动启动。（故事2、3）
- **FR-015**: 系统必须同时展示整体状态及各动作的待执行、执行中、完成、带原因跳过、失败、结果不明、停止状态；前项失败/不明/停止后不执行后项。（故事2）
- **FR-016**: 系统必须关联会话内动作证据、工资、护理前后状态、课程完成、用时占用及停止原因；只有全部选中项完成或按明确条件合法跳过才标记方案完成。（故事2）
- **FR-017**: 系统必须限制单设备同一时间一个运行会话；重复启动拒绝，不能并行消费。（边界场景）
- **FR-018**: 验收必须分别取得三项独立运行以及四项多动作组合的设备证据；严格打工后学习还必须由同一会话真实触发工作、到账、护理和课程完成，历史分开运行不能替代。（故事1～3）
- **FR-019**: 打工必须在同次岗位成本确认后，对当前体力、清洁分别满足实际耗值且剩余分钟满足实际时长才授权输入；任一必要值未知、过期或岗位成本冲突时阻断，不受护理目标影响。（故事1、3）
- **FR-020**: 护理必须区分库存已知与未知，按健康缺口和道具实际增益计算所需件数，扣除确认可用库存后才计算购买缺口；未知库存不得伪造零库存或已证实的资金短缺。（故事1～3）
- **FR-021**: 确需购买时必须在付款前独立确认真实可用金币、购买数量与总价、会话购买额度，以及后续全部未付学费仍可保留；任一必要资金信息未知则不付款，付款结果未知不重复付款。（故事1～3）
- **FR-022**: 方案必须保留逐步资源轨迹，计入工作后的体力/清洁下降、库存消耗及购买、各剩余学习节的真实学费和分钟，并在每步完成后以实际观察重算；预测收益不能作为到账或消费授权。（故事2、3）

### Key Entities

- **动作配置**: 打工岗位与触发条件、护理目标阈值、学习课程和节数；只在选中相应动作时必填。
- **方案**: 所选动作、明确执行顺序、每日用时上限及可追溯配置版本。
- **执行会话**: 单次独立动作或组合方案的配置快照、动作进度、整体结果和证据关联。
- **动作结果**: 执行状态、完成或跳过依据、停止原因、未知副作用及资源观察。
- **课程档案**: 课程名称、时长、可选状态和读取完整性。
- **工作结果**: 岗位、时长、完成证据、工资证据及可用资源观察。
- **健康观察**: 体力、清洁及观测时间，工作/护理按需要验证；学习仅可选记录，不作学习门禁。
- **库存观察**: 每类道具的已确认可用件数、数量证据和未知原因，决定护理购买缺口。
- **资源状态与就绪判断**: 真实钱包、健康、库存、时间与后续未付学费的同一状态快照，以及按动作给出的可执行/需观察/不足原因。
- **资源轨迹**: 每步前后资源及预测/真实依据；学习可记录课程页实际健康消耗及课后变化，但不据此设健康开课门槛或硬编码健康消耗为零。
- **每日用时记录**: 工作与学习共用的保守占用记录，区分实际完成与已占用但执行结果不明确。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 设备上打工、护理、学习各独立成功一次，三份会话记录中未选动作执行与消费次数均为0；独立打工和护理在无课程档案时仍能通过。
- **SC-002**: 四个多动作组合（打工+护理、打工+学习、护理+学习、打工+护理+学习）各成功一次，执行顺序与显示方案一致，未选动作次数为0，全部选中项有完成或合法跳过证据。
- **SC-003**: 三动作组合至少一次取得同会话真实打工完成、正数工资到账、护理达标和所选课程完成证据；另一次按需工作在资金不足时真实触发并闭环，资金充足时能够明确记为跳过。
- **SC-004**: 保存并重启后，七种非空动作组合的选项与参数回读全部一致，旧方案迁移后课程、阈值、预算和按需工作语义保持一致。
- **SC-005**: 不存在课程、开课未确认、工资未确认、必要数值不可读、预算不足、重复启动六类异常全部遵循停止或拒绝规则，错误完成记录与自动重复支付均为0。
- **SC-006**: 正常返回、入口重入、未知页面、恢复耗尽四类恢复验收各一次，均满足故事5；恢复尝试不超过三次。
- **SC-007**: 每份验收记录都可逐项核对执行前后每日用时变化；重复观察、恢复及应用重开导致的重复占用次数为0；结果不明的保守占用可见。
